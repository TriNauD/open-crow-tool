# 截图上传 — Context

> **来源**：BRAINSTORM 需求池 **C-2**（[`待办-C-截图上传.md`](../BRAINSTORM需求池/待办-C-截图上传.md)）  
> **立项性质**：**前瞻立项文档**（文档先行）。待阶段 2 / 排期确认后再编码。

## 背景 / 痛点

- 首页 placeholder 已暗示「截图文字」，但**无**文件选择、粘贴图片或多模态请求。
- 用户常从聊天/文档截图专有名词，希望「丢图就能解释」。

## 现状（调研）

| 项 | 结论 |
|----|------|
| UI | `app/page.tsx` 仅 textarea |
| API | `/api/explain` 仅文本 messages |
| Provider | 配置里可出现支持 vision 的模型名，但**从未**组 `image_url` / base64 多模态消息 |
| 存储 | 无用户图片 bucket / 上传 API |

## 约束

- **成本与配额**：图片 token 显著高于文本；须限大小、分辨率、每用户频率。
- **隐私**：默认不长期存原图（或短 TTL）；日志禁止打 base64。
- **安全**：校验 MIME（png/jpeg/webp）、魔数、最大字节；防任意文件上传当图。
- 扩展侧截图（tab capture）可二期；MVP 建议 **仅 Web**。

## 关键决策（待用户确认）

| 选项 | 说明 | 推荐默认 |
|------|------|----------|
| **输入方式** | 粘贴 / 文件选择 / 二者 | **二者**（粘贴优先） |
| **处理路径** | 客户端压缩 → 请求内联 base64 vs 先上传 Storage 再传 URL | **MVP：压缩后 inline**（免 Storage 运维）；超限再逼降分辨率 |
| **模型** | 必须 vision 能力的 primary；失败降级文案「请改用文字」 | **推荐** |
| **是否 OCR 再文本解释** | 先 OCR 再走旧文本链 | 备选；多一步延迟 |

**最大尺寸建议**：原图 ≤ 2MB；最长边 ≤ 1280px；每分钟 N 次（与现有 rate limit 策略对齐时再定）。

## 依赖与风险

- **依赖**：`lib/ai/providers.ts` 实际模型是否支持 vision；Vercel body size 限制。
- **风险**：供应商 vision 价差大；Preview/生产模型不一致导致「本地行、线上不行」。
- **与 D-1**：截图 ≠ 链接抓取；勿混同一 API，除非后续做统一「附件」抽象。
